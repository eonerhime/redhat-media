- **Roadmap:** [`../roadmap.md`](../roadmap.md), Milestone 1, Phase 15

- **Started:** 2026-10-16
- **Status:** approved by the owner, 2026-10-16

## What and why

The public site is complete (Phases 3–14). Next comes the Milestone 1 release (Phase 16), which replaces the static page on the production URL. Before that release, the site has to fail gracefully, prove its performance and accessibility budgets, and give the team a way to hear about trouble. Today:

- an unknown URL shows Next's unbranded default 404 (a bare "404" heading, with no header, footer or way back);
- an error outside the page area (in the header, the footer or a layout) shows Next's default error screen;
- there is no analytics and no field performance data;
- accessibility has been checked for contrast, focus, reduced motion and the mobile nav, but has never had a full audit;
- Lighthouse has never been measured;
- nothing alerts anyone if the site or the database is down, and no Firewall rules or runbooks exist.

This phase closes those gaps and runs the pre-launch security checklist from `tech-stack.md`.

One finding shapes the whole phase: **Vercel's Hobby plan cannot send error alerts.** Vercel *Alerts* need Pro with Observability Plus, Log Drains need Pro, and Hobby keeps runtime logs for one hour. Neon has no connection or query alerts on any plan; its Free plan only emails usage warnings. Alerting is therefore built on **GitHub Actions**, which works on every plan (D7). The same research raised a launch blocker for the owner: Hobby is for non-commercial use only (owner question A).

## Out of scope

- The production go-live: production env vars, production roles, the restore rehearsal, Search Console, the custom domain and the external validators (Phase 16).
- Vercel Alerts, Log Drains and Observability Plus. These need Pro, and Alerts also need the paid Observability Plus add-on. If the owner upgrades (question A), adding them is a follow-up amendment, not a blocker.
- Error capture inside the app (`instrumentation.ts` `onRequestError` sending to an error service). Sending errors anywhere needs a new vendor or a Pro log drain. The monitor (D7) catches outages, and Phase 36 adds operational visibility.
- A CSP reporting endpoint (`report-to`). Phase 14 deferred it here. It stays out: it would be a public POST route needing rate limiting and storage, and `csp.spec.ts` already fails on any violation, in CI and on every preview.
- Analytics custom events, such as inquiry conversions. They are a Pro feature, and the inquiry form only arrives in Phase 18.
- Changing the soft 404 on unknown slugs. It is kept (Phase 14 D10). The page it shows becomes the branded one.
- Failed-login security logs (Phase 24) and recurring drills (Phase 35).

## Constraints

- **C1 — Libraries.** `@vercel/analytics` and `@vercel/speed-insights` are already approved. `@axe-core/playwright` and `lighthouse` (in place of `@lhci/cli`, D6 amended) are added to `tech-stack.md` in this PR, as devDependencies with exact pins (owner answers B and C). Nothing else is added.
- **C2 — Static stays static.** No page changes rendering mode. The analytics components are client components in the root layout and read no request data. The route table is compared with develop's CI log (plan 7.1).
- **C3 — No schema change.** No migration and no seed change.
- **C4 — The CSP is unchanged** (D3). If a change turns out to be needed, it lands with its test and `tech-stack.md` (`CLAUDE.md`).
- **C5 — Nothing goes to `main`.** The monitor's schedule and dispatch start working at Phase 16. This phase proves them through the label trigger.
- **C6 — Secrets stay out of public output.** No secret goes into a log, report, artifact or issue. The Actions logs and artifacts of this public repository can be read by anyone.
- **C7 — Existing suites hold.** `pnpm test`, `pnpm test:db` and `pnpm test:e2e` pass. Existing specs change only where they assert Next's default 404 (`service-pages.spec.ts` expects an `h1` of "404" "until Phase 15").
