# Tech Stack — RedHat Media Platform

This file is the approved list of technologies. Adding a library that is not listed here needs this file to be updated first (see README §2).

The current site is one static `index.html` with inline CSS and no build step. It is replaced in full by the stack below. Its copy, contact details and brand colours are carried over (see *Design tokens*).

## Architectural rules

1. **Server-first rendering.** Public pages are Server Components, statically generated or ISR. `/portfolio` is partially prerendered: its shell is static, and the filtered listing renders per request from the cached portfolio read (Phase 11 spec, D2). `/portfolio/[slug]` is prerendered for every published slug; a slug published after a deploy renders on its first request and is then cached, with no redeploy (Phase 12 spec, D1). **Public server components never read the login session**, so the pages stay static (see *In-place CMS*). Use client components only where interaction requires them: filters, the inquiry stepper, the lightbox, the portfolio modal, video facades and edit controls. The portfolio modal opens only from the `/portfolio` grid; elsewhere a card loads the full page (Phase 22 spec, D2).
2. **Filter state lives in the URL** (`/portfolio?category=web-apps`). Filtered views can then be shared and indexed. The filters are plain links: no parameter means All, then `web-apps` (`WEB_APP`), `photography`, `videography` and `marketing` (`DIGITAL_MARKETING`, `SOCIAL_MEDIA` and `ONLINE_PRESENCE`). A filter with no published items is hidden, and an unknown or empty `category` value shows All (Phase 11 spec, D1, D3). Portfolio items have real pages at `/portfolio/[slug]`; the in-grid modal (Phase 22) is an intercepting route over the same URL, so deep links always work (Phase 22 spec, D1–D4).
3. **Services are configuration, not database rows.** The six services are a typed config in `content/services.ts`, keyed by `ServiceCategory`, grouped into three pillars, with their copy read through `block()`:
   - **Production:** Photography, Videography.
   - **Growth:** Digital Marketing, Social Media Marketing, Online Presence Management.
   - **Build:** Web & App Development.

   **Each service can be muted.** The config holds a `muted` default (false for all six), and from Phase 31 a `ServiceSetting` row overrides it, the same way `ContentBlock` overrides `content/defaults.ts`. Public code never filters the raw list; it reads services through one helper (`visibleServices()`, from Phase 2). From Phase 3, ESLint enforces this: `app/**` and `components/**` cannot import the raw `services` value or `content/defaults` (copy goes through `block()`). A muted service is hidden **everywhere** a visitor can reach:
   - the homepage pillars, `/services` and any nav or footer listing (a pillar whose services are all muted is hidden too);
   - its `/services/[slug]` page, which returns 404 (static params still list all six, so unmuting needs no redeploy);
   - `sitemap.ts` and JSON-LD;
   - the inquiry form and stepper choices, the `?service=` pre-fill (ignored), and **server-side inquiry validation**, which rejects a muted service.

   Muting changes nothing else. Its copy, media, past inquiries and portfolio items are kept, so unmuting restores the service as it was. Portfolio items in a matching category stay published, and only their "Start a project" pre-fill drops the muted service. At least one service must stay visible.
4. **Save first, then email.** The inquiry server action writes to Neon *before* calling Resend. An email failure is logged and shown to admins, and is never shown to the client as a lost submission.
5. **Server-side authorisation everywhere.** Every mutation (server action or route handler) starts with `await requireRole(minRole)` from `lib/auth/guards.ts`. The role hierarchy is `sales` < `editor` < `admin`. The check re-reads the session and role from the database and returns a typed result: `{ ok: true, staff }` (`userId`, `role`, `name`), or `{ ok: false, status, reason }`. It is **401** when no staff member is signed in, the user is deactivated or the CMS is off. It is **403** for a role below the minimum (`"role"`), a user who has not set up 2FA (`"2fa"`), or, with `{ fresh: true }`, a sign-in older than 15 minutes (`"reauth"`). A route handler returns `guardResponse(result)`; a server action returns a generic error. Every 403 writes an `auth.forbidden` security log line (Phase 25 spec, D1–D3, D12). `proxy.ts` may redirect `/admin` for UX only. The role the browser receives only decides whether edit controls appear; it is never trusted.
6. **Staff entry at `/admin`**, as in MRU (Phase 24 spec, D13, amended by the owner on 2026-10-26). The public site shows visitors **no login link, button or footer mention** of staff access.
   - `/admin` is the sign-in. After sign-in and the 2FA code, staff land on the **website itself**. Editing happens on the real pages, through the Editing: On/Off toggle (Phase 26), never in a separate editing interface.
   - Signed-in staff see an **admin icon in the site header**, labelled with their role ("Admin panel", "Editor panel", "Sales panel"). It opens `/admin/panel`, home of the non-editing tools under `/admin/*`: the inquiry inbox (Phase 32), staff management and the audit log (Phase 33). Visitors never see it. The shared `EditModeProvider` asks the server who is signed in only when a sign-in hint is set in `localStorage`, and the icon reads its answer, so public pages stay static and visitors make no auth request (Phase 26 spec, D2). The icon is a full page load, not a client navigation.
   - A visitor who is not signed in and opens any other `/admin/*` page is sent to `/admin`.
   - Every `/admin` page has a **"Back to the website"** link in its header bar, so staff can return to the site, including after signing out (owner, 2026-10-27; Phase 26 spec, D12).
   - Every `/admin` page sends `noindex, nofollow` (both the meta tag and the `X-Robots-Tag` header) and is left out of `sitemap.ts`. It is **not** listed in `robots.txt`, because a `Disallow: /admin` line would advertise the path.
   - Login errors are generic ("Invalid email or password"). Every staff form is `method="post"` and can't be submitted until the page has hydrated, so a credential never lands in a URL.
   - `/admin` is a path bots probe. The rate limits, lockout and 2FA protect it; an unlinked path is **not** a security control. Rule 5 still applies.
7. **Secrets** live only in Vercel environment variables. `.env.example` is committed and `.env*` files are git-ignored. Nothing prefixed `NEXT_PUBLIC_` may be a secret.
8. **Errors.** Every data-fetching route has a `loading.tsx` and an `error.tsx`. One `app/(public)/error.tsx` serves every public route, except the intercepted portfolio modal, which has its own loading and error states inside the dialog so a failure there leaves the grid in place (Phase 22 spec, D8); its copy is fixed text in `lib/site.ts`, not content blocks, so it still renders when the content store is what failed (Phase 10 spec, D6). From Phase 15, `app/error.tsx` and `app/global-error.tsx` catch errors in the layouts with the same copy. One branded `<NotFoundView>` (copy in `lib/site.ts`, `notFoundCopy`) serves both `notFound()` in public pages and unmatched URLs, inside the shared `<PublicShell>` (Phase 15 spec, D1, D2). Cached data reads return a failure result instead of throwing, because a throw inside `"use cache"` fails the prerender. Server actions return typed `{ ok, error }` results and do not throw to the client. The client **always** checks the result, keeps the editor or form open on failure, and shows the error.
9. **SEO.** Use the Metadata API on every route through one helper, `pageMetadata()` in `lib/seo/metadata.ts` (title, description, canonical, Open Graph, Twitter card). The root layout sets `metadataBase` from `env.siteUrl`, so previews never claim production URLs (Phase 14 spec, D1). Plus:
   - **Canonical URLs:** every public route sends one for its own path, with no query string. The exception is `/portfolio`, which sends none, so its filtered views stay indexable (rule 2). Pages marked `noindex` (an unknown slug, the unavailable state) send no canonical (Phase 14 spec, D2).
   - **Open Graph images** (1200 × 630 PNG, `next/og`):
     - a site card for `/`, `/services`, `/about`, `/portfolio` and `/contact`;
     - a card per service;
     - a card per portfolio item, built from its Cloudinary cover.

     A muted, unknown or coverless item, or a failed read, falls back to the site card. The cards render inside `"use cache"` helpers (`lib/seo/og-images.ts`), so they prerender (Phase 14 spec, D3).
   - `sitemap.ts` (visible services and published items only; it still lists the other pages when the portfolio read fails) and `robots.ts` (no `Disallow` lines, rule 6).
   - JSON-LD, with every business value taken from `lib/site.ts`:
     - `Organization` on `/` (`@id` `{siteUrl}/#organization`);
     - `LocalBusiness` (Lagos, city only) on `/contact`, whose `parentOrganization` points at that `@id` (Phase 14 spec, D6);
     - `Service` per service page, `CreativeWork` per portfolio item (these name that `@id` as provider and creator) and `VideoObject` for embedded videos. Portfolio items use `CreativeWork` whatever their category: Google's Software App result requires a price and a rating or review, which RHM's case studies do not have and must not invent (Phase 12 spec, D10). `VideoObject` carries `uploadDate` only when it is known; Phase 30 decides how to record it.
10. **Accessibility.** Semantic HTML, visible focus states, WCAG 2.2 AA contrast and `prefers-reduced-motion` respected. Every image has alt text, and the editor requires it. Every edit control is keyboard-reachable and labelled.
11. **Performance budget.** Mobile Lighthouse ≥ 90 on every public template. The LCP image is prioritised, every other image is lazy-loaded through Cloudinary responsive transforms, and no iframe loads before a click.
12. **Content Security Policy.** One enforced policy from Phase 14 (`lib/security/headers.ts`). `img-src` allows Cloudinary and video-thumbnail hosts. `frame-src` allows only `www.youtube-nocookie.com`, `player.vimeo.com` and, from Phase 18, `challenges.cloudflare.com`. From Phase 18, `https://challenges.cloudflare.com` is also in `script-src` and `connect-src`, the three directives Cloudflare documents for Turnstile (Phase 18 spec, D5). From Phase 28, `connect-src` also allows `https://api.cloudinary.com`, where the staff editor posts signed uploads (Phase 28 spec, D11).
    - **`script-src` keeps `'unsafe-inline'`.** Next.js renders inline bootstrap and RSC payload scripts on every page, and they differ per page and per build. A static header cannot list hashes for them, and nonces would make every page dynamic (rule 1).
    - **SRI was measured and not adopted.** A Phase 14 build with `experimental.sri` and `script-src 'self'` logged 560 violations across 17 templates, so the flag is not used (Phase 14 spec, D7).
    - **`style-src` keeps `'unsafe-inline'`** for `next/font`, `next/image` and React `style` props.
    - **XSS defence** therefore rests on React escaping, the lint bans on `dangerouslySetInnerHTML` and `*RawUnsafe`, `<JsonLd>` escaping, and no `'unsafe-eval'` or wildcard sources outside `pnpm dev`.
13. **Cache refresh after writes.** Every CMS mutation refreshes the affected routes with tag APIs: inside a Server Action, `updateTag(tag)` from `next/cache`, so the editor's next render reads the write (Phase 27 spec, D6). All copy is one cached read of every `ContentBlock` row, `readContentBlocks()` in `lib/content/read.ts`, tagged `content` (`cacheLife("days")`, the pages' own lifetime, and `minutes` after a failed read, which shows the defaults); `block()` reads it, and `updateContentBlock` refreshes that one tag. Public portfolio reads are cached functions in `lib/portfolio/read.ts`, all tagged `portfolio` (`cacheLife("hours")`): the list read and, from Phase 12, the per-item read behind `/portfolio/[slug]`. Phase 31's portfolio mutations refresh that one tag (Phase 10 spec, D2; Phase 12 spec, D2).

## In-place CMS ("Editing: On/Off")

This follows the same pattern as the Epenal Group platform, which fixed known gaps in the `memories-r-us` and `cecilia-onerhime` reference projects.

### Roles

| Role | Can do |
| --- | --- |
| `sales` | Inquiry inbox in the admin panel (`/admin/…`): view inquiries and change their status. No edit toggle. |
| `editor` | Everything `sales` can, plus the edit toggle: text blocks, images, videos, portfolio items and muting or unmuting services. |
| `admin` | Everything `editor` can, plus staff user management and the audit log. |

### How it works

1. **`EditModeProvider`** (client, `components/cms/edit-mode.tsx`) wraps the page frame in `<PublicShell>`, only where `CMS_ENABLED` is on, so production pages carry none of it until Phase 34. After the page loads in the browser, and again on every navigation, it calls `GET /api/cms/session`, but only when the sign-in hint is set (rule 6). The endpoint is `no-store` and always returns a 200 with `{ role, authenticated }`. `authenticated` is true for any signed-in, active staff member. `role` stays `null` until they have set up 2FA, so no staff UI appears before then. A request with no session cookie is answered without a database read, and the endpoint is a 404 while `CMS_ENABLED` is off. This is the page's **one** session read: the header's admin icon reads the role from the provider (Phase 25 spec, D8, D9; Phase 26 spec, D1–D3). The state lives in a module store read with `useSyncExternalStore`, never in React context: a context change above a Suspense boundary that is still streaming makes React client-render it and leaves a hidden duplicate of the streamed HTML (Phase 26 spec, D1 amended). A failed request keeps the last known role. Public pages therefore stay static.
2. When the role is `editor` or higher, a fixed bottom-right **"Editing: Off" / "Editing: On"** pill appears: a button with `aria-pressed`, dark with an outline when Off and filled with the button red when On. It holds only the toggle; the admin panel and Sign out stay behind the header's admin icon (rule 6). Editing **starts Off** after sign-in. The toggle (`rhm:editMode`) and the last-known role (`rhm:role`) are kept in `sessionStorage` and read only after the page has loaded, so the pill does not flicker on navigation and a new tab starts Off. Sign-out clears both, and the toggle is dropped whenever the session answers with no editor role (Phase 26 spec, D4–D7).
3. While editing is on, every editable text block, image, gallery, video and portfolio field shows a **✎ button**. It is always visible, not only on hover, so it works on touch screens and for keyboard users. It is focusable and labelled "Edit {label}" (Phase 24 spec, D16; the pattern in memories-r-us and cecilia-onerhime). With editing off, no ✎ is rendered. Only one editor dialog can be open at a time. Escape closes it (Phase 27 spec, D2).
4. **Text, `<Editable blockKey value>`** (Phase 27 spec, D1–D9):
   - The ✎ sits just after the text, never inside a link or button, and out of the flow, so turning editing on moves nothing (Phase 27 spec, D9 amended). It is labelled `Edit "<first 40 characters>"`. It opens a native `<dialog>` editor, as in MRU: an input for a label, and a wrapping textarea for everything else. A heading or line stays one line (Enter saves, and a pasted line break becomes a space); only body copy keeps line breaks (owner, 2026-10-28).
   - Only keys listed in `lib/content/editable.ts` can be edited: the copy visitors read on the public pages. Inquiry form copy, metadata, OG cards, the error page and email-only keys keep their defaults. Each listed key has a kind with a character cap: `label` 40, `heading` 120, `line` 300, `body` 5,000. Only `body` takes line breaks and **bold** (`**…**`, rendered as `<strong>` through React elements, never HTML).
   - Saves through server action `updateContentBlock`. The action checks `requireRole("editor")`, then a per-editor `rateLimit` (60 saves per 10 minutes), then a Zod check that the key matches `^(home|about|services|portfolio|contact|footer|privacy)\.[a-zA-Z0-9.]+$` (`privacy` from Phase 18, for the privacy notice), is listed, and that the trimmed value fits its kind. It then upserts, with a `content.update` `AuditEvent` holding `before` and `after` in the same transaction, and calls `updateTag("content")`.
   - Saving an empty value deletes the row (`content.reset`), so the page falls back to its default.
   - Defaults live in `content/defaults.ts`, read through `block(key)`. This applies from Phase 2, so turning on editing later needs no rewrite.
5. **Images, `<EditableImage slot>` and `<EditableGallery owner>`**:
   - Editors can upload, replace, delete, drag-to-reorder, and edit **alt text** (required) and captions.
   - Image slots are listed in `lib/media/slots.ts`, each with its owner, folder, aspect and a **default image in code**, which shows while the slot has no row, as `content/defaults.ts` does for copy. A page slot holds at most one `MediaItem` (Phase 28 spec, D2, D4, D7).
   - The ✎ sits on the image's corner, so nothing moves, and opens a dialog: replace, required alt text (≤ 150 characters, one line), and Remove back to the default. The browser posts the file straight to `api.cloudinary.com` with our own picker and a signed `fetch`, with no upload widget (Phase 28 spec, D3, D5).
   - The server action `signCloudinaryUpload` **picks the full public ID** (`rhm/{ownerType}/{slot folder}/{env}/{random}`, where `{env}` is `production`, `preview` or `local`) and signs it with the allowed formats (jpg, png, webp, avif). A signed upload cannot cap size, so the 15 MB maximum is checked in the browser and again by `attachMedia` (Phase 28 spec, D6).
   - `attachMedia` verifies the public ID sits under that slot's folder **for this environment**, then reads the asset through the Admin API: one over 15 MB or in another format is destroyed and refused. An unchanged public ID saves only the alt text. `removeMedia` deletes the row (Phase 28 spec, D9).
   - Replace and remove call Cloudinary `destroy` on the old asset after the database change, **only** for an upload from the current environment: a default, a seed asset or another environment's upload is never destroyed, because one Cloudinary cloud serves every environment. Any failure is logged. The actions share a per-editor `rateLimit` (30 per 10 minutes) and audit `media.replace`, `media.alt` and `media.remove` with `before` and `after` (Phase 28 spec, D9, D10).
6. **Video by URL**:
   - Server action `attachVideo` accepts only YouTube (`watch`, `youtu.be`, `/shorts/`, `/embed/`) and Vimeo (`vimeo.com/{id}`, `player.vimeo.com/video/{id}`). Anything else is rejected with a clear error.
   - The database stores the provider, the video ID and the canonical URL, never embed HTML.
   - Public rendering is a thumbnail facade. The `<iframe>` (`youtube-nocookie.com`, `player.vimeo.com`) is injected only on click.
7. **Portfolio items in place**:
   - Pencils on detail fields map to `updateRecordField`, with a fixed list of editable fields and a typed Zod schema per field.
   - Editors toggle Draft/Published and Featured on cards.
   - "Add item" opens a modal. Delete asks for confirmation and removes the item's Cloudinary assets.
8. **Service muting in place** (rule 3):
   - With editing on, each service card on `/services` and on the homepage pillars shows a **Mute** toggle. A muted service is no longer in the static page, so `/services` also shows a "Muted services" tray, which lists them with **Unmute**. The tray's data comes from a `no-store` endpoint that only editors and admins can read, so visitors' HTML never contains muted services.
   - Server action `setServiceMuted(category, muted)` checks `requireRole("editor")` and validates `category` against the `ServiceCategory` enum with Zod. It refuses to mute the last visible service, then upserts the `ServiceSetting` row.
   - The action refreshes every route that lists services: `/`, `/services`, the service's own page, `/contact` and the sitemap.
   - Turning editing off shows exactly what a visitor sees (mission principle 10).
9. **After every change:** refresh the affected routes (rule 13) and write an `AuditEvent`.

From Phase 28, a partial unique index on `MediaItem ("ownerId") WHERE "ownerType" = 'PAGE'` keeps one image per page slot, with the slot key (e.g. `home.hero`) as `ownerId` (Phase 28 spec, D7). | Already match the Epenal-proven design. The index makes "one hero image" a database rule, so a race fails instead of leaving two rows; gallery owners keep many rows. |
| `AuditEvent` (Phase 25): `actorId` is **nullable** and has **no foreign key**, with an extra `[actorId, createdAt]` index. The table is **append-only**: `rhm_app` may only insert and select (Phase 25 spec, D4, D6). | The system (a lockout) and the owner scripts have no actor. A history must outlive the users it names, and an `ON DELETE SET NULL` would need UPDATE. The index serves Phase 33's "an editor's edits" view. |

## Environment variables

`lib/env.ts` validates variables with Zod at build time. The schema **grows per phase**: a variable becomes required in the phase that first uses it, never earlier. `NEXT_PUBLIC_CLOUDINARY_CLOUD_NAME` is required on Vercel `preview` and `production` from Phase 8. It is public, so CI sets it as a plain value. `NEXT_PUBLIC_CLOUDINARY_API_KEY` and `CLOUDINARY_API_SECRET` exist from Phase 9 **only in the developer's `.env.local`**, for `pnpm media:upload-seed`; they are not in `lib/env.ts`, Vercel or CI until Phase 28 (Phase 8 spec, D4; Phase 9 spec, D6). From Phase 28 both are in `lib/env.ts`, required on Vercel wherever `CMS_ENABLED=1` (Preview now, Production from Phase 34). Vercel holds a **second API key used only by the site**, with the secret marked Sensitive, so the developer's seed key and the site's can be rotated apart. CI builds with placeholders, because every Cloudinary call in CI is stubbed (Phase 28 spec, D11, D13). `NEXT_PUBLIC_SITE_URL` is required when `VERCEL_ENV=production`. On previews it falls back to `https://$VERCEL_BRANCH_URL`, and locally to `http://localhost:3000`.

From Phase 18, `INQUIRY_FORM_ENABLED` (server-only, `1` = on) switches the inquiry form. It is `1` on Vercel Preview, in CI and in `.env.example`, and **on in Production from the Phase 20 release**, once the team notification is sent (Phase 20 spec, D11). Wherever it is on, `NEXT_PUBLIC_TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` are required. Vercel Production holds the one real widget's keys, and `lib/env.ts` **refuses Cloudflare's test keys** when `VERCEL_ENV=production`. Preview, local and CI use the test keys (site key `1x00000000000000000000AA`, secret `1x0000000000000000000000000000000AA`), which always pass (Phase 18 spec, D5, D10).

From Phase 20 (Phase 20 spec, D8, D9), all server-only: `RESEND_API_KEY` (a **sending-only** key, one for Production and one for Preview), `EMAIL_FROM` (`Name <address>`), `INQUIRY_NOTIFICATION_EMAIL` (1–5 comma-separated addresses), `INQUIRY_ACK_ENABLED` (`1` = send the client acknowledgment) and `EMAIL_REDIRECT_TO` (one address that replaces every recipient). On Vercel with the form on, the first three are **required**. `EMAIL_REDIRECT_TO` is **refused in production**, and `INQUIRY_ACK_ENABLED=1` is **refused in production while `EMAIL_FROM` is `@resend.dev`**. Vercel Preview redirects to `delivered@resend.dev` with the acknowledgment on. CI and local runs have no key, so every send is skipped and logged.

From Phase 24 (Phase 24 spec, D9, D11), both server-only: `CMS_ENABLED` (`1` = staff sign-in and `/admin` on) is `1` on Vercel Preview, in CI and in `.env.example`, and **unset in Production until the Milestone 3 release (Phase 34)**; while it is off, `/admin/*` and `/api/auth/*` return 404, and the header carries no admin icon. Wherever it is on, `BETTER_AUTH_SECRET` (at least 32 characters) is required. Better Auth's base URL is the site URL above, so there is no `BETTER_AUTH_URL`.

GitHub Actions-only secrets (never in Vercel): `MIGRATOR_DATABASE_URL` (Phase 7, stored in the GitHub Environment `neon-preview` and used only by the `migrate-preview` job; from Phase 16 the production `rhm_migrator` is in the Environment `neon-production`, used only by `migrate-production`, beside `VERCEL_DEPLOY_HOOK_URL`, the production deploy hook) and `VERCEL_AUTOMATION_BYPASS_SECRET` (Phase 0, used by the preview header check). `MONITOR_DATABASE_URL` (Phase 15) is an `rhm_readonly` direct connection in the GitHub Environment `monitor` (limited to `main`): the preview branch in Phase 15, production from Phase 16. Beside it, the repository variable `MONITOR_BASE_URL` holds the origin the monitor checks (Phase 15 spec, D7). `RETENTION_DATABASE_URL` (Phase 23) is the production `rhm_retention`, direct connection, in the GitHub Environment `retention` (limited to `main`), used only by the retention workflow (Phase 23 spec, D8). `BOOTSTRAP_DATABASE_URL` (a branch's `neondb_owner` URL) exists only in the owner's terminal while `scripts/db-bootstrap.mts` runs, and is never stored. On Vercel the build fails if `MIGRATOR_DATABASE_URL`, `BOOTSTRAP_DATABASE_URL` or (from Phase 23) `RETENTION_DATABASE_URL` is set, and `DATABASE_URL` must use the `rhm_app` role with `sslmode=require` (Phase 7 spec, D7).
